# Сканы → Markdown

Всё, от чего зависит точность, делает код: что считать расхождением, как собирается итоговый текст, когда решения устарели. Модели только читают страницы и разбирают споры, человек сверяет. Ты — исполнитель: запускаешь диспетчер и делаешь ровно то, что он назвал.

`run.py` ниже — это `python3 ${CLAUDE_PLUGIN_ROOT}/skills/scan-to-markdown/scripts/run.py`. Все команды — из корня проекта.

## Что инструмент создаёт в проекте

| Папка | Что там | Кто пишет |
|---|---|---|
| `inbox/` | новые сканы (PDF), ещё не разобранные. Отсюда инструмент берёт работу по умолчанию | человек кладёт |
| `documents/` | итог: каждый скан и его Markdown рядом, с одинаковым именем. Это постоянное содержимое проекта, от инструмента оно не зависит | код переносит скан и пишет Markdown |
| `logs/scan-to-markdown/` | лог разбора: настройки (`settings.json`), оба чтения, распознавание Vision, расхождения, решения арбитра, отметки и правки человека | код, модели, человек через страницу сверки |
| `logs/scan-to-markdown/cache/` | картинки страниц, полосы, вырезки — пересоздаются, в git не попадают | код |

- **Как документ движется.** Скан лежит в `inbox/`, пока его не разобрали. После первой сборки код переносит его в `documents/` и кладёт рядом `<имя>.md` с `verified: false`. Когда человек сверил все страницы — `verified: true`. Значит, `inbox/` пуст, когда всё разобрано, а несверенное видно по `verified: false`.
- **Имена папок** по умолчанию — `inbox/` и `documents/`. Если человек хочет другие, выполни `run.py init --inbox <имя> --documents <имя>`. Можно и позже: init обновит настройки, а содержимое старой папки перенеси целиком через `git mv`. Сканы найдутся по имени файла.
- **Имя файла** `ГГГГ-ММ-ДД_Учреждение_Название.pdf` даёт дату, учреждение и название в свойствах Markdown. Другое имя тоже подходит: тогда название — это имя файла. Шаблон задаётся в `settings.json` (`name_pattern`).
- **Лог** нужен для истории и для продолжения работы. `documents/` от него не зависят: лог можно удалить или убрать из git, документы и их статус сверки останутся.
- **Обновление инструмента не трогает готовые страницы.** Страница, по которой уже есть решения арбитра, сохраняет своё сравнение, пока не изменились её чтения: текст и отметка сверки остаются. Пересравнить такую страницу новой логикой — только по просьбе человека: `python3 ${CLAUDE_PLUGIN_ROOT}/skills/scan-to-markdown/scripts/compare.py <часть имени> --redo`, затем шаг 3 (арбитр решит заново, отметку сверки страницы придётся поставить снова).
- **Чужие файлы не трогаются.** Markdown в `documents/`, сделанный не этим инструментом, не перезаписывается. Если имя нового скана уже занято в `documents/`, диспетчер останавливается.

## Алгоритм

1. **Найди корень проекта** — папку с `logs/scan-to-markdown/settings.json`. Если её нет, спроси человека, где будет проект и подходят ли ему имена папок `inbox/` и `documents/`. Затем выполни там `run.py init` (с `--inbox`/`--documents`, если нужны другие имена): он создаст папки, папку лога и проверит инструменты. Сканы человек кладёт во входящую папку.
2. **Оцени объём**, если работы много: `run.py status` печатает число страниц ещё не подготовленных сканов. Новых страниц больше пяти — назови человеку число страниц и оценку и продолжай после его согласия. Оценка на страницу: около 0,35 млн токенов и около 4 минут работы. Страницы порции читаются и разбираются параллельно, поэтому порция из нескольких документов занимает 5–25 минут; дольше всего работает арбитр.
3. **Выполни `run.py advance`** (можно с частями имён документов) и действуй по последнему блоку вывода:
   - `ACTION read` или `ACTION arbitrate` — запусти инструмент Workflow: `scriptPath` из вывода, `args` — содержимое названного JSON-файла, переданное как JSON-значение, а не строкой. Дождись завершения и повтори шаг 3.
   - `ACTION corrections` — по каждой странице из списка: прочитай комментарий, посмотри место на скане (`zoom.py` из той же папки), запиши файл правок по формату ниже. Повтори шаг 3.
   - `WAIT review` — запусти в фоне страницу сверки (команда в выводе), дай человеку ссылку и блок «Как сверять» из вывода. Остановись: дальше ход за человеком.
   - `DONE` — сообщи, какие документы готовы. Все они в `documents/`.
   - `STOP` — перескажи ошибку дословно и остановись. Не обходи её.
4. Если после выполненного действия диспетчер снова выдаёт то же самое — остановись и сообщи человеку: что-то пошло не так.

## Файл правок

`logs/scan-to-markdown/corrections/<документ>/p<N>.json`. Правки применяются к собранному тексту страницы (`logs/scan-to-markdown/final/<документ>/p<N>.md`) последними и показываются человеку фиолетовым.

```json
{
  "corrections": [
    {"find": "точный фрагмент собранного текста", "replace": "как напечатано на скане", "region": [41.5, 43, 10, 60], "comment": "комментарий человека дословно"}
  ],
  "replies": [
    {"comment": "комментарий человека дословно", "reply": "ответ, если правка не нужна"}
  ]
}
```

- `find` должен встречаться в собранном тексте ровно один раз — бери фрагмент вместе с соседними словами.
- `region` — где это место на скане: `[верх, низ, лево, право]` в процентах, как в `zoom.py`.
- `comment` — дословная копия комментария: по ней диспетчер понимает, что комментарий обработан.
- Решай по скану, а не по комментарию. Если на скане не так, как пишет человек, — не правь, а ответь в `replies`, что видно на скане. Вопрос без правки — тоже в `replies`.
- Прежние правки не удаляй: файл только дополняется.

## Нельзя

- Править руками Markdown в `documents/`, тексты читателей, решения арбитра и `review-status.json` — у каждого свой хозяин (код, модели, человек).
- Переносить или переименовывать отдельные файлы в `documents/` и `inbox/` — это делает код. Переименовать папку целиком по просьбе человека можно (см. «Имена папок»).
- Менять правила, модели и настройки посреди прогона.
- Коммитить без явного согласия человека.
